# 과제 1. 유닉스 환경 프로세스·스레드·메모리 분석 보고서

> 대상 서비스: `ai-interview-coach` (RAG 기반 AI 면접 코치, FastAPI + Docker)
> 실행 환경: AWS EC2 `t3.small` (Ubuntu, vCPU 2, RAM 1.9GB, swap 0B)
> 관찰 도구: `/proc`, `top -H`, `docker stats`, `docker inspect`

---

## 1. 배경과 목적

이 서비스는 사용자 답변을 받아 Gemini API로 채점·코칭하는 구조라, 요청 하나를 처리하는 데 외부 LLM API 호출이 여러 번 발생한다. 사전에 응답 시간을 측정한 결과 **응답 시간의 대부분이 LLM 응답 대기**였다. 이 보고서는 그 "대기"가 실제로 프로세스·스레드·메모리 레벨에서 어떤 상태로 나타나는지를 리눅스 표준 도구로 직접 관찰하고 분석한다.

관찰은 실제 리눅스 서버(EC2)에서 수행했다. 개발 환경인 macOS에는 `/proc` 파일시스템이 없어 이 분석이 불가능하므로, 배포를 먼저 완료한 것이 본 과제의 전제 조건이었다.

### 도구 선택 메모
컨테이너 이미지를 경량(slim) 베이스로 만든 탓에 `ps` 명령이 포함되어 있지 않았다. 그래서 `ps` 대신 `/proc/1/status`와 `/proc/1/task/`를 직접 읽고, 호스트에서는 `top -H`(스레드 단위 표시)를 사용했다. 이는 "경량 이미지는 크기를 줄이는 대신 디버깅 도구가 빠진다"는 트레이드오프를 실제로 겪은 사례다.

---

## 2. 평상시 프로세스·스레드 구조

요청이 없는 유휴 상태에서 컨테이너의 메인 프로세스(PID 1, uvicorn)를 조회했다.

```
/proc/1/status
  Name:    uvicorn
  State:   S (sleeping)
  VmRSS:   557840 kB   (약 545MB)
  Threads: 9
```

`top -H`로 본 9개 스레드는 **전원 S(sleeping)** 상태, CPU는 91~100% idle이었다.

### 분석
- **프로세스는 1개, 스레드는 9개**다. 스레드 구성은 uvicorn 워커들 + `jemalloc`(메모리 할당자) 1개다.
- `top -H`에서 9개 스레드의 RES(물리 메모리)가 모두 `557840`으로 **동일**했다. 이는 스레드가 프로세스의 메모리 공간을 **공유**하기 때문이다. 프로세스라면 각자 독립된 메모리를 가지지만, 스레드는 하나의 메모리를 나눠 쓴다. 프로세스와 스레드의 핵심 차이를 육안으로 확인한 지점이다.
- CPU 항목에 `st`(steal time) 8.7%가 관측됐다. `t3.small`은 물리 서버를 여러 가상 머신이 공유하는 인스턴스라, 다른 VM에 CPU를 빼앗긴 비율이 나타난 것이다.

## 3. 단일 요청 처리 중 상태 전이

요청 하나를 보내며 `top -H`를 1초 간격으로 스냅샷하여, 프로세스 상태(State)·스레드 수·CPU·메모리의 변화를 추적했다.

| 국면 | 스레드 수 | State | CPU | 메모리(RES) | 해석 |
|---|---|---|---|---|---|
| 평상시 | 9 | S | idle 100% | 557MB | 요청 없음, 대기 |
| I/O 대기 | 18 | **D** | wa 35% | 725MB | 인터럽트 불가 대기 |
| 연산 | 20 | **R** | 80% | 967MB | 응답 파싱·객체 변환 |
| 종료 후 | 20 | S | idle 100% | 979MB | 다시 대기 |

리눅스 프로세스 상태 문자의 의미:
- **R (Running)**: CPU를 사용해 실제 연산 중
- **S (Sleeping)**: 인터럽트 가능한 대기 (주로 네트워크 응답 대기)
- **D (Disk sleep)**: 인터럽트 불가능한 대기 (디스크 I/O, 메모리 확보 등)

### 분석
**(1) 스레드 풀 동작.** 요청이 들어오자 스레드가 9개에서 20개로 늘었고, **처리가 끝난 뒤에도 20개로 유지**됐다. 이는 매 요청마다 스레드를 새로 만들고 없애는 비용을 피하기 위해, 한 번 만든 스레드를 재사용하려고 남겨두는 **스레드 풀** 방식이다. "안 줄어드는 것"이 아니라 "재사용하려고 일부러 남기는 것"이다.

**(2) 대기 중심의 처리.** 전체 처리 시간의 대부분은 S(대기) 상태였다. 다만 그 사이에 짧은 R(응답 파싱·Pydantic 객체 변환 등 CPU 연산)과 D(메모리 확보 등 I/O 대기)가 끼어 있었다. 즉 순수한 네트워크 대기만은 아니고, "대기 사이사이에 짧고 굵은 연산"이 있는 구조다. 시간 측정만으로는 "느리다"까지만 알 수 있지만, 상태 관찰을 해야 "그 시간 동안 무엇을 하고 있었는지"까지 보인다.

**(3) 메모리 피크.** 요청 1건이 순간적으로 967MB까지 사용했다. 컨테이너 한도(1.86GB)의 절반이다. swap이 0B이므로, 여기서 동시 요청이 겹치면 메모리 부족(OOM)으로 죽을 수 있다고 예상했다.

## 4. 동시 요청 부하 테스트

3절에서 세운 "동시 요청 시 OOM 위험" 가설을 검증하기 위해, 요청 5개를 동시에 발사하고 메모리와 종료 여부를 관찰했다.

**예상**: 메모리가 5배로 겹쳐 폭증하거나, 자원 부족으로 요청이 순차 처리되어 지연이 계단식(15/30/45/60/75초)으로 늘어날 것.

**실측 결과**:

| 항목 | 값 |
|---|---|
| 5개 요청 응답 시간 | 15.5 / 17.6 / 18.3 / 19.3 / 22.9초 |
| 메모리 사용 | 589MB에서 거의 변화 없음 |
| OOM 발생 여부 | `OOMKilled: false` |
| 재시작 횟수 | `RestartCount: 0` |

### 분석: 가설이 반증되며 더 정확한 결론에 도달
5개 요청이 계단식이 아니라 **거의 동시에**(15~23초 사이) 완료됐다. 순차 처리였다면 마지막 요청이 75초쯤 걸렸어야 하는데 그렇지 않았다. **vCPU 2개짜리 서버가 5개 요청을 동시에 처리한 것이다.**

CPU가 2개뿐인데 5개를 동시에 처리할 수 있었던 이유는, 이 작업이 **I/O 바운드**이기 때문이다. 처리 시간의 대부분이 CPU 연산이 아니라 외부 LLM API의 응답을 기다리는 시간(S 상태)이라, CPU는 놀면서 5개의 "기다림"을 동시에 떠안을 수 있다. 만약 CPU를 계속 쓰는 CPU 바운드 작업이었다면 vCPU 2개로는 5개 동시 처리가 불가능했을 것이다.

메모리도 폭증하지 않았다. 967MB 피크는 "응답 파싱" 순간에만 잠깐 발생하는데, 5개 요청의 파싱 시점이 서로 어긋나 겹치지 않았기 때문이다. 대기 상태(S)는 메모리를 거의 쓰지 않는다.

이 결과는 프로젝트 지식 문서(`kb/async_sync.md`)에 서술한 "I/O 바운드 작업에서는 비동기 처리가 유리하다"는 원리를, 그 문서를 서빙하는 서버 자신에서 실측으로 증명한 사례다.

---

## 5. 한계

동시 요청 5개에서 가장 느린 요청은 22.9초로, 단일 요청(약 20초)보다 늘었다. 응답을 파싱하는 순간에는 vCPU 2개를 두고 경합이 생기므로 완전히 공짜는 아니다. 요청이 수십 개로 늘면 이 경합이 병목이 될 것이다. 또한 `OOMKilled: false`는 이 워크로드(I/O 바운드) 기준이며, CPU 바운드 작업이거나 요청 수가 크게 늘면 결과가 달라질 수 있다.

---

## 6. 결론

1. **추정을 측정이 정정했다.** "swap 0 + 얇은 여유 메모리라 동시 요청 시 OOM"이라는 사전 추정은 틀렸다. 이 워크로드는 대기 중심이라 메모리를 거의 쓰지 않아 안전했다. 측정하지 않았다면 잘못된 결론(예: "인스턴스 사양을 올려야 한다")에 도달했을 것이다.
2. **프로세스/스레드/메모리 세 축과 R/S/D 상태 전이**를 실제 서버에서 관찰했고, 예상을 뒤집는 발견(I/O 바운드의 동시성 확장)까지 확인했다.
3. 프로세스와 스레드의 차이(메모리 공유), 스레드 풀, 상태 문자의 의미를 교과서가 아니라 자신의 서비스에서 직접 눈으로 확인했다.
