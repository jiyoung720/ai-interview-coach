# Authorization 헤더와 Bearer 토큰

HTTP 요청에 Access Token을 실어 보낼 때는 `Authorization` 헤더를 사용한다. 형식은 `Authorization: Bearer <토큰>`이며, `Bearer`는 "이 토큰을 가진 사람에게 권한을 준다"는 인증 방식을 나타내는 이름이다. JWT를 서버에 전달할 때도 이 헤더에 담는다.

토큰을 URL 쿼리 파라미터에 넣지 않는 이유는 노출 경로가 많기 때문이다. 쿼리는 서버 접근 로그에 그대로 기록되고, 브라우저 방문 기록과 북마크에도 남으며, 다른 사이트로 이동할 때 Referer 헤더에 실려 나갈 수 있다. 헤더는 이런 경로로 새어 나가지 않는다.

`Authorization` 헤더 방식은 쿠키와 달리 브라우저가 자동으로 붙여주지 않는다. 클라이언트가 매 요청마다 명시적으로 담아야 한다. 번거로워 보이지만 이 점이 CSRF 공격을 막아준다. 공격자가 사용자를 속여 요청을 보내게 하더라도 토큰이 자동으로 실리지 않기 때문이다. 반대로 쿠키는 자동 전송되므로 SameSite 같은 별도 방어가 필요하다.

다만 헤더 방식은 토큰을 클라이언트 어딘가에 저장해둬야 한다는 문제가 남는다. JavaScript로 접근 가능한 곳에 두면 XSS 공격에 탈취될 수 있다. 그래서 XSS와 CSRF 중 무엇을 더 경계하느냐에 따라 헤더 방식과 HttpOnly 쿠키 방식 중에서 고르게 된다.

서버는 이 헤더에서 토큰을 꺼내 서명을 검증하고 사용자를 식별한다. REST의 무상태성 원칙에 따라 서버가 요청 간 상태를 기억하지 않으므로, 인증 정보도 매 요청에 함께 보내야 한다. 토큰이 없거나 만료됐으면 401을, 토큰은 유효하지만 권한이 부족하면 403을 반환한다.
